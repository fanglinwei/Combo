# Combo 远程更新设计方案

日期：2026-10-08。状态：产品设计已确认；根据用户没有正式 Apple 开发者证书的条件修订发布路径，工程可行性待实测。本文描述新增需求，不代表当前应用已实现。

## 1. 已确认的目标与范围

用户已确认以下推荐方案：

- 手动入口位于“设置 → 关于与帮助”。
- 支持 App 内下载；用户确认后安装并重启。
- 默认开启自动检查，每 24 小时检查一次，可随时关闭。
- 第一版只接收稳定版。
- 自动发现更新时采用“面板设置入口旁提示 + 关于页显示可用版本”，不主动弹窗、不申请系统通知权限。
- GitHub Releases 托管安装包，GitHub Pages 托管更新源与说明；目标网络实测不通过再调整。
- 用户目前没有正式 Apple 开发者证书。第一版按 ad-hoc 应用签名 + Sparkle EdDSA 更新包签名设计；Developer ID 签名与 Apple 公证调整为未来增强项，不作为第一版开发前提。

采用 Sparkle 2，设置入口使用 Combo 现有 SwiftUI 组件，更新说明、下载、校验、安装与重启优先使用 Sparkle 标准界面。自动检查不授权自动下载或静默安装。

第一版不增加 Beta 切换、强制升级、自动下载安装偏好、增量包、更新账户系统或自建安装器。后续有明确需求时再扩展。Debug 构建使用测试源或禁用更新，避免向正式用户源发布本地测试包。

第一版仍以 App 内下载、安装和重启为目标；无证书路径必须用实际发布包验证，不能只据框架文档宣布 Combo 已可升级。如果真实更新链路无法通过测试，阻止该安装路径发布，并使用同一 Sparkle 更新源提供“前往下载”的信息型更新作为备用交付方式，不绕过签名检查或系统拦截。

## 2. 现状与接入条件

| 当前事实 | 对方案的影响 |
| --- | --- |
| `SettingsView.swift` 的关于与帮助已有品牌版本、能力、帮助与隐私内容 | 在版本卡片下增加软件更新分组，沿用现有字体、颜色、间距和按钮样式 |
| `Info.plist` 中 `LSUIElement = true` | 按菜单栏应用设计低打扰提醒，检查时不抢其他应用焦点 |
| marketing/build version 当前均为 `1.0.0` | 将内部构建号改为独立、单调递增的数字；展示版本继续使用语义版本 |
| 当前部署目标 macOS 26、打包脚本只构建 arm64 | 首期发布范围保持 macOS 26+、Apple Silicon，不暗示已支持 Intel |
| 当前主 App、Helper 与 dylib 使用 ad-hoc 签名，没有公证 | 第一版验证所有嵌套组件及 Sparkle 辅助程序的签名结构、加载与安装；更新包必须有 EdDSA 签名，不声称已公证 |
| 当前未接入 Sparkle，也没有仓库内 GitHub Actions 发布配置 | 新增框架与发布步骤；初期允许在受保护的发布 Mac 上执行，不要求先建设 CI |

本地依据：[设置页面](../Combo/Views/SettingsView.swift)、[应用元信息](../Combo/App/Info.plist)、[Xcode 工程](../Combo.xcodeproj/project.pbxproj)、[DMG 打包脚本](../Releases/package-dmg.sh)、[打包说明](../Releases/packaging/README.md)。

没有正式 Apple 开发者证书是用户已明确提供的约束。第一版不要求 Team ID，不为了接入更新改变当前 bundle ID；实际分发身份与更新私钥在接入阶段核验。未来改变 `local.combo.app` 必须单独规划迁移，因为改变身份可能影响偏好、登录项和系统权限连续性。

## 3. 开源项目参考与选择理由

| 项目 | 已查证的做法 | Combo 采用的部分 |

推荐 Sparkle 的原因是 Combo 的主要价值在系统状态与控制体验，维护下载校验、替换自身、权限提升和重启机制会扩大工程范围。使用标准更新框架可以把维护集中在产品策略与发布质量上。这是基于参考实现和 Combo 现状作出的设计判断。

## 4. 设置页设计

关于与帮助顺序为：品牌与当前版本 → 软件更新 → 当前能力 → 使用帮助 → 隐私与状态边界。

| 元素 | 文案与行为 |
| --- | --- |
| 分组标题 | 软件更新 / Software Updates |
| 手动按钮 | 检查更新… / Check for Updates… |
| 自动开关 | 自动检查更新 / Automatically check for updates |
| 默认说明 | 每天检查新版本，下载和安装由你确认。 |
| 关闭后的说明 | 自动检查已关闭，你仍可手动检查更新。 |
| 检查记录 | 上次成功检查：今天 14:30；从未成功时显示“尚未检查” |
| 可用版本 | Combo 1.x.x 可用，操作为“查看更新…” |
| 检查失败 | 无法检查更新，请稍后重试。需要时显示简短具体原因 |

以框架是否允许新检查控制按钮可用性。已有更新会话时不创建第二个；存在可展示窗口时优先回到该窗口，无法展示时保留清楚的忙碌状态。关闭设置窗口不取消已经开始的下载，也不退出更新器。

时间按当前语言和时区格式化。键盘可以访问所有操作，状态不只靠颜色区分，VoiceOver 只播报有意义的状态变化，不逐帧播报下载进度。最小窗口、中文、英文、深浅外观和增强对比度均需验证。

## 5. 手动检查与下载安装

1. 用户点击“检查更新…”，显示检查中，并启动用户发起的检查。
2. 查询失败时显示原因与重试入口；不能将失败当成“已是最新版本”。
3. 查询成功且无适用更新时显示“你使用的是最新版本”；成功时间随之更新。
4. 有更新时展示新旧版本、发布日期、更新说明和主要操作。
5. 用户选择下载安装后开始下载，显示进度并允许取消；下载失败可重试。
6. 更新包校验通过后提示安装与重启。若所选 Sparkle 标准界面版本的确认顺序不同，接入时对照实测锁定最终文案；必须保留用户对安装/退出的明确授权。
7. 安装前保存应用偏好，按既有退出逻辑结束临时演示和运行中的组件；安装由 Sparkle 执行。
8. 新版重启后正常进入菜单栏，按原有偏好恢复运行。首次成功更新不额外弹出营销窗口。

更新说明使用简洁的“新增 / 改进 / 修复”结构，涉及权限或兼容性改变时明确说明。存在不兼容新版时，说明最低系统要求，并提供发布页面；不要只显示一个容易误解的“最新版本”。Sparkle 支持系统要求过滤和对应的手动检查反馈。[发布文档](https://sparkle-project.org/documentation/publishing/)

“稍后提醒”和“跳过此版本”交给标准更新会话处理。主动检查应允许用户重新查看已跳过的更新。标准按钮名称与行为需要在锁定的 Sparkle 版本中实测，不在 Combo 中另造一套跳过版本存储。

## 6. 自动检查与提醒（已确认）

自动检查开关默认开启，周期为 24 小时；由 Sparkle 维护调度，Combo 不另设轮询计时器。启动恢复调度，不每次启动额外强制检查。用户关闭后停止未来的后台检查，手动操作保持可用。已发生的请求或用户已经发起的下载不因开关变化而伪装成取消。

已确认提醒方式：

- 自动检查无更新时无提示，失败时无弹窗；关于页保留可查看的状态。
- 有更新时，在 Combo 操作面板的设置入口旁显示轻量文本提示，并在关于页显示可用版本。
- 保持主菜单栏图标现有电量、网络与音量语义，不用更新提示替换核心状态。
- 用户点击后展示 Sparkle 更新窗口，不因为自动发现更新主动抢焦点。
- 第一版不申请系统通知权限、不播放声音、不新增常驻 Dock 图标。
- 第一版普通更新与紧急修复均不强制退出；发布紧急修复时加强更新说明，提醒仍服从上述低打扰策略。

Sparkle 的 Gentle Reminders 接口可以在保留标准更新窗口的同时定制后台提醒。菜单栏应用应专门验证启动期间和非启动期间的焦点行为，不能只依赖普通前台应用的默认表现。[轻量提醒文档](https://sparkle-project.org/documentation/gentle-reminders/)

提醒状态必须跟随框架会话变化，不能在用户跳过、安装完成或会话终止后保留失效入口。重启后重新获取可用更新；没有足够依据时不显示过时的可用版本。暂不增加独立的定时弹窗提醒机制。

## 7. 客户端接入边界

只需一个应用生命周期内持续存在的更新协调对象，持有 `SPUStandardUpdaterController`，提供设置绑定、检查可用性与轻量提醒状态。应用启动创建一次，关于页与面板共享该对象，避免每次打开设置重新启动更新器。

| 职责 | 归属 |
| --- | --- |
| 定时检查、版本选择、下载、校验、安装、标准窗口 | Sparkle |
| 关于页、自动检查开关、低打扰提醒、用户文案 | Combo |
| 构建、签名、公证、包发布、更新源生成 | 发布流程 |

手动入口调用标准检查 API，按钮状态观察 `canCheckForUpdates`。自动检查偏好直接绑定 `automaticallyChecksForUpdates`，不维护第二份同义 UserDefaults；恢复显示偏好不修改更新设置。实现依据：[程序化接入](https://sparkle-project.org/documentation/programmatic-setup/)、[SPUUpdater API](https://sparkle-project.github.io/documentation/api-reference/Classes/SPUUpdater.html)。

建议配置 `SUEnableAutomaticChecks = YES`、`SUScheduledCheckInterval = 86400`、`SUAutomaticallyUpdate = NO`，并通过 `SUAllowsAutomaticUpdates = NO` 隐藏标准窗口中允许静默自动更新的选择，保持第一版“每次由用户确认”的产品边界。保留系统分析默认关闭。接入时用锁定框架版本验证设置含义。[配置文档](https://sparkle-project.org/documentation/customization/)

## 8. 远程更新源（已确认）

初期 GitHub Releases 托管安装包，GitHub Pages 托管固定地址的稳定版 `appcast.xml` 和更新说明。使用实际仓库与可控的长期地址，文档中的结构不代表这些地址已经部署。

客户端 → HTTPS appcast → 适用稳定版信息 → 用户确认下载 → GitHub Releases 安装包 → 校验 → 安装与重启。

不将 GitHub `releases/latest` API 作为默认版本判断源，也不把登录令牌放入客户端。以维护者明确发布的 appcast 控制更新范围。第一版不建设动态后端和镜像回退；上线前在目标用户网络中测试元数据与安装包下载，实际不可达时调整托管方案。

| appcast 信息 | 设计要求 |
| --- | --- |
| `sparkle:version` | 递增内部构建号，与包内 `CFBundleVersion` 一致 |
| `sparkle:shortVersionString` | 用户可读版本，与包内 marketing version 一致 |
| `pubDate` | 真实发布日期 |
| 更新说明 | 版本固定地址或内嵌说明，不包含跟踪资源 |
| `sparkle:minimumSystemVersion` | 第一版为当前支持的 macOS 26.0.0 |
| 平台/架构约束 | 仅向支持设备提供 arm64 包；按锁定 Sparkle 版本验证兼容的过滤字段 |
| `enclosure` | 版本固定的 HTTPS 包地址、实际长度与 EdDSA 签名 |
| 发布页面链接 | 查询、兼容性或安装失败时的人工路径 |

appcast 使用 `generate_appcast` 生成，避免手工计算签名和长度。保留经过验证的旧兼容版本。第一版仅提供全量包，不发布 delta。Sparkle 支持 DMG，因此可以复用 Combo 的分发格式。[接入文档](https://sparkle-project.org/documentation/)

## 9. 签名、公证与隐私

### 9.1 无 Apple 证书的第一版

ad-hoc 应用签名保证包内代码签名结构，但不能提供 Apple 认可的开发者身份；Sparkle EdDSA 验证更新包与客户端内置公钥的对应关系。第一版要求 HTTPS、有效的包签名、受保护的 EdDSA 私钥与完整升级演练。

Sparkle 维护者明确讨论了 unsigned/ad-hoc 应用的安装保护与支持；Developer ID 仍是官方推荐的分发方式。这里的结论是“无证书可以验证完整更新路径”，不是“Combo 已通过验证”。第一版使用普通 App bundle 的 DMG 更新，不采用安装器 PKG。[Sparkle 维护者说明](https://github.com/sparkle-project/Sparkle/discussions/2764)

主应用、所有 Helper/dylib 与 Sparkle 内嵌程序均需要验证。保持现有非沙盒、Hardened Runtime 关闭的 ad-hoc 发布配置作为验证起点，不在无证书方案中直接套用 Developer ID 的 archive/export 分发模式。使用官方 Sparkle 包，按其嵌入要求保留符号链接、执行权限与各组件的签名/entitlements，逐项验证框架加载与辅助进程。不能通过对整个包盲目递归重签来掩盖组件问题，也不为了加载框架新增全局系统安全关闭步骤。[Sparkle 接入文档](https://sparkle-project.org/documentation/)

首次从互联网下载安装时，macOS 可能拦截未识别开发者或未公证应用。帮助文档应链接 Apple 的“隐私与安全性 → 仍要打开”官方流程，并说明仅适用于用户确认来源可信的场景；受管理设备可能不允许该操作。不要承诺“首次批准后所有更新绝不再弹窗”，须验证目标 macOS 的真实下载、替换、重启与权限表现，不只在同一开发机内测试。更新组件不自动关闭 Gatekeeper，也不以删除 quarantine 标记作为产品功能。[Apple 安装说明](https://support.apple.com/en-us/102445)

私钥保存在受保护的发布 Mac 钥匙串或 CI 密钥存储中，做好可恢复备份；仓库和公开服务器只存公钥、清单与签名结果。没有 Developer ID 时，不依赖其作为 EdDSA 密钥丢失后的轮换备用信任路径；私钥丢失时按需安排人工重新安装可信版本。保持公钥、bundle ID 与升级路径稳定。[签名与密钥说明](https://sparkle-project.org/documentation/)

### 9.2 未来获得 Developer ID 后

将 Developer ID 代码签名、Hardened Runtime、Apple 公证与适用的票据装订纳入发布流程，验证所有嵌套组件。媒体、AirPods 和控制功能需逐项实测，不能为了完成公证笼统关闭保护。保持原 EdDSA 公钥与应用身份，测试 ad-hoc → Developer ID 更新、登录项与权限连续性，再切换分发路径；不在同一次未经验证的迁移中同时更换多个信任凭据。

### 9.3 更新源与隐私

第一版最低要求是更新包签名。更新源与更新说明签名作为接入评估项：Sparkle 2.9+ 提供支持，但开启后需要签名更新源和说明、核验轮换与失败策略，并承担对应发布维护工作；不把它描述成已启用的能力。[配置文档](https://sparkle-project.org/documentation/customization/)

关于页隐私说明补充：“检查更新时会连接更新服务器获取版本信息；不会上传电量、网络状态、音量或媒体内容。关闭自动检查后，仅在你手动检查或继续更新流程时连接。”不声称完全不联网或完全匿名：托管服务仍可能看到 IP 地址和常规请求信息。关闭 Sparkle 系统分析，不增加设备标识、账户或使用行为统计。实际网络行为应通过抓包验收。

## 10. 发布顺序与事故处理

1. 确定 marketing version 与更高的内部构建号。
2. 构建 Release arm64 包，运行项目现有验证及核心功能回归。
3. 验证所有组件的 ad-hoc 签名、框架加载与最终 DMG；当前无证书不执行 Developer ID 签名、公证或票据装订。未来证书模式另增加这些步骤。
4. 使用最终字节生成 EdDSA 签名与 appcast；签名后不再改安装包。
5. 上传版本固定安装包与更新说明，验证匿名下载、大小、签名和系统兼容性。
6. 用测试源完成真实旧版 → 新版升级。
7. 最后发布正式 appcast，确认客户端看到正确版本。

发布失败不更新正式 appcast。发现问题时撤下问题版本对应清单项以阻止后续发现；已下载或安装的用户不保证能被远程撤回。修复版使用更高构建号重新发布，不修改已公开的同名包，不对用户自动降级。人工重新安装的兼容性与偏好格式需验证。

现有版本没有更新框架，因此已安装的旧版用户需要手动安装一次首个支持更新的版本。该版本必须内置有效更新源与公钥，此后才能进入 App 内升级链路。即使当前继续采用 ad-hoc，新包也需要验证辅助功能、登录项和其他权限连续性；未来 ad-hoc → Developer ID 迁移另行演练，不能承诺系统一定保留原授权。

## 11. 界面状态与错误处理

| 状态/场景 | 用户可见结果 | 行为 |
| --- | --- | --- |
| 尚未检查 | 尚未检查 | 手动入口可用 |
| 检查中 | 正在检查… | 防止重复会话 |
| 检查成功，无适用更新 | 已是最新版本 | 刷新成功时间 |
| 可用更新 | Combo 1.x.x 可用 | 查看更新说明 |
| 下载中 | 进度与取消入口 | 不覆盖当前安装 |
| 验证中 | 正在验证更新… | 不提供绕过校验操作 |
| 可安装 | 安装与重启的明确操作 | 保存状态，等待授权 |
| 离线/超时/服务错误 | 无法检查或下载，请重试 | 自动失败不弹窗；手动失败明确反馈 |
| 更新包被篡改/签名不符 | 更新验证失败 | 终止安装，保留当前版本 |
| 系统/架构不兼容 | 说明具体要求 | 保留旧版，提供发布页 |
| DMG 只读运行/路径不可更新 | 提示安装至应用程序文件夹 | 不重复失败；验证框架默认静默情形 |
| 权限不足 | 系统授权或人工安装路径 | 不自建提权脚本，不假装成功 |
| 用户取消安装/授权 | 返回可理解的状态 | 当前应用保持可用 |
| 安装失败 | 明确失败与人工恢复入口 | 实测恢复结果，不承诺所有失败都自动回滚 |

只读路径与 App Translocation 是重点：Sparkle 某些默认流程不会主动提示不可更新情况，Combo 必须通过可用的框架接口和实际路径检查补齐用户反馈。[接入文档](https://sparkle-project.org/documentation/)

## 12. 实施拆分与验收

### 阶段 A：发布条件验证

核验现有应用身份、更新源托管权限与 EdDSA 密钥；锁定含适用安全修复的 Sparkle 2 稳定版本。验证实际 ad-hoc Release 的 Helper、dylib、Sparkle 辅助程序与最终 DMG；无需等候购买 Apple 证书。不以本地 Debug 构建通过代替真实下载包验证。

### 阶段 B：最小客户端接入

一个共享更新协调对象；关于页按钮、自动检查开关与成功时间；标准窗口下载与安装；稳定版过滤；测试源和正式源隔离。

### 阶段 C：菜单栏体验

按确认后的提醒策略接入 Gentle Reminders；补充隐私文案、中英文与可访问性。检查设置窗口与更新窗口的焦点、关闭、重复打开和后台下载行为。

### 阶段 D：真实发布演练

使用两个 ad-hoc 签名、EdDSA 更新包签名有效且构建号不同的实际分发版本，在另一台或干净的测试 Mac 上走真实下载、首次批准、检查、安装与重启链路；保留日志与人工恢复说明。只有演练完成才将正式 appcast 指向实际更新包。若安装链路不通过，使用 Sparkle 信息型更新让用户前往 Releases 下载，不把安装失败隐藏成成功。[信息型更新文档](https://sparkle-project.org/documentation/publishing/#downloading-from-a-web-site)

| 验收组 | 必须覆盖 |
| --- | --- |
| 设置与调度 | 默认开启；关闭后无未来后台检查；重启保存选择；恢复显示偏好不重置更新偏好；成功时间不被失败刷新 |
| 交互 | 手动检查全部结果；重复点击；取消下载与授权；设置关闭后更新会话保持合理；跳过版本与主动检查 |
| 低打扰 | 有/无更新、启动/非启动、其他应用前台、全屏场景；无抢焦点、无声音或通知权限请求 |
| 服务与安全 | 离线、超时、404/5xx、清单损坏、包截断、错误签名、不兼容系统/架构、测试源隔离 |
| 安装 | 真实互联网下载后的首次系统拦截/批准、`/Applications`、权限不足、DMG 运行、取消、失败恢复、旧版 → 新版、连续两个更新；不可安装时的信息型更新 |
| 产品连续性 | 偏好、语言主题、菜单栏、登录项、媒体读取、AirPods、Wi-Fi 与充电控制、授权状态 |
| 可访问性 | 中文英文、最小窗口、键盘、VoiceOver、深浅外观、增强对比度与减少动态效果 |

文档阶段未运行客户端测试，未部署更新源，未签名或发布安装包。上述清单是后续实现的验收要求。

## 13. 决策记录与下一步

- 第一轮：用户已确认 App 内完整更新、默认每天自动检查和稳定版优先。
- 第二轮：用户已确认面板轻量提示、关于页状态与 GitHub Releases + GitHub Pages 托管。
- 条件更新：用户明确没有正式 Apple 开发者证书，因此将 Developer ID 与公证从第一版前提调整为未来增强项。第一版按 ad-hoc + EdDSA 进行工程验证，保留 App 内完整更新目标。

下一步优先执行阶段 A 和一次最小 ad-hoc → ad-hoc 更新演练，再接入正式产品界面。现阶段仍需核验托管权限、更新密钥与实际升级兼容性；文档不假定这些条件已经具备，也不把没有 Apple 证书误写成无法检查或无法使用 Sparkle。

维护者首次准备与每次发布的操作清单见 [Sparkle 接入与发布清单](sparkle-release-checklist.md)。
