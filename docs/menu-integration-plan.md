# Combo 系统菜单整合：方案对照与实施计划

更新于 2026-09-23。本文是系统图标折叠的**当前决策入口**；[Thaw 源码核查](thaw-menu-folding-research.md)、[macOS 27 备用路径调研](macos27-menu-folding-research.md)和[系统设置手动隐藏调研](menu-bar-hiding-research.md)保留各方案的证据与细节。**Combo 当前只保存折叠选择并进行只读菜单检测，尚未折叠系统图标，也未验证原生菜单展开。**

## 目标与已确认的产品行为

- 从 macOS 27 开始支持这一功能。第一轮只处理 Wi‑Fi、声音／AirPods、电池；日期／时钟单独验证，不纳入首轮承诺。
- “整合系统菜单”总开关默认关闭。Wi‑Fi、声音／AirPods、电池初始选中，但每项可以独立取消；未选项必须保持可见。关闭总开关应恢复已折叠项，并保留用户的选择。
- 点击 Combo 打开面板，再选择对应入口。Combo 可以短暂显示原系统图标，打开**真正的系统菜单**，待菜单关闭后重新折叠。不得用自绘面板冒充 Wi‑Fi 选网、AirPods 降噪／空间音频或电池菜单。
- 某一项无法唯一识别、折叠或稳定打开原生菜单时，该项保持可见；其他已验证项可以继续工作。不能只凭用户勾选或辅助功能已授权就显示“折叠成功”。
- Combo 需要辅助功能权限来定位、移动或操作菜单项。优先验证无需屏幕录制的路径。检测到 Bartender 等菜单栏管理器正在管理同一布局时，提示用户先退出它，再启用 Combo 折叠；Combo 不代用户结束该应用。

## 四种方案对照

| 方案 | 折叠方式 | 三项独立选择 | Combo 内打开原生菜单 | 结论 |
| --- | --- | --- | --- | --- |
| **Thaw 式分区与临时展开** | 使用自身的 `NSStatusItem` 分隔区；识别系统项后以 Command 拖动放入隐藏区，长分隔项将其移出可见范围 | 机制上可逐项移动；macOS 27 实机尚未证明 | 临时移回可见区，点击实时目标，菜单结束后拖回；尚未在本机验证 | **首选实验路径**。最贴近既定交互，但使用私有 CGS 窗口枚举，需验证 macOS 27 的窗口模型、拖动与恢复 |
| **MenuBarClientCore 私有白名单** | 激活系统菜单项允许列表，把指定系统 ID 排除 | 理论上可以，但 ID 和行为均不受公开契约保证 | 需要暂时释放限制、确认目标可见并唤起菜单，再重新限制；已有项目报告点击可能被限制拦截 | **精确折叠的技术备用**。单项实验通过前不能接入设置开关 |
| **Ice 式公开 spacer + 系统 overflow** | 扩展 Combo 自己的窄状态项，把其左侧项目推入 macOS 的 `«` 溢出区 | **不能自动按三个开关精确选择**；依赖用户手动摆放系统图标 | 可经系统 overflow 操作，Combo 的逐项原生菜单入口还需另行验证 | **交互降级备用**。若采用，界面须明确写“按位置折叠”，不能保留“独立自动折叠”的承诺 |
| **系统设置手动隐藏** | 用户在 macOS 设置中关闭对应状态项显示 | 用户可分别设置，但 Combo 不控制或自动恢复 | 原菜单栏图标已不在，通常需通过控制中心／系统设置操作 | **人工兜底**，不满足 Combo 一键展开系统菜单的目标 |

Thaw 的[公开源码](thaw-menu-folding-research.md)证明了分区、识别、移动、临时展开的实现链路，但其 **macOS 27 的 `thaw-next` 源码是私有的**。不能据公开的 macOS 26 代码宣称该链路已在 macOS 27 可用。Ice 和 MenuBarClientCore 的证据、实验 ID 与限制见[备用路径调研](macos27-menu-folding-research.md)。Thaw 为 GPL-3.0；在分发许可未决定前，只参考机制与事实，Combo 不直接移植其源码。

## 当前实测与权限边界

用户已为当前 Combo.app 授予辅助功能权限。应用内只读检测查询 `com.apple.controlcenter` 和 `com.apple.systemuiserver` 的 `AXMenuBar`、`AXExtrasMenuBar`，四个根属性均返回 `-25212`（`kAXErrorNoValue`），未得到目标菜单项。**这只说明旧探针的这两个入口没有值**，不等于 `MenuBarAgent`、各项目所属应用的 AX extras 路径，或 Thaw 的窗口枚举路径不可用。当前没有对系统图标执行点击、拖动或折叠。

较早的 macOS 26 SDK CLI 探针通过编译和参数保护检查，但执行进程当时未获辅助功能权限；它不能证明原生菜单或折叠可用。历史探针位于 `prototypes/menu-access/`，应用内当前检测位于 `Combo/MenuDiagnostics.swift`。旧的“先在 Control Center 根项找三个标识，再 AXPress”的顺序已被上述 macOS 27 结果取代。

## 推荐实施顺序

1. **只读识别。** 在已授权的 Combo GUI 进程里验证 macOS 27 的 `MenuBarAgent`／所属应用 AX extras 路径与 Thaw 式窗口枚举；对 Wi‑Fi、声音、电池分别取得唯一的实时身份、几何位置及可执行操作。不根据标题或硬编码私有 ID 直接移动图标。
2. **单项可逆实验。** 先选一项验证分区、移动、折叠与恢复；记录原位置并核实目标状态。任一步失败即保持该项可见。不能把 `10,000 pt` 分隔项在旧版本有效当作 macOS 27 通过的证据。
3. **原生菜单闭环。** 从 Combo 面板临时露出该项，确认系统菜单真实打开；以菜单消失和目标稳定为条件重新折叠，不只按固定延时或点击返回码判断成功。
4. **扩到三项并接设置。** 每项单独验证后才允许对应开关生效。覆盖正常退出、崩溃后重启、权限撤销、系统菜单进程重启、睡眠唤醒、刘海屏／外接屏、全屏、菜单栏自动隐藏和用户改动图标顺序。
5. **首选路径不成立时换备选。** 优先单项验证 MenuBarClientCore 是否能隐藏并重新打开真实原生菜单；若仍失败，可提供明确标为“按位置折叠”的 Ice 式模式。系统设置手动隐藏始终作为说明性兜底，不能标记为 Combo 自动折叠。

验收以**实际可见状态、原生菜单可操作、关闭后能恢复，以及未选图标不受影响**为准。失去定位、权限或恢复能力时，停止折叠并解除 Combo 自身能解除的占位／限制，向用户说明未恢复的项目；不能承诺在辅助功能被撤销后仍可自动恢复 macOS 保存的图标顺序。私有接口失败、系统版本变化或其他管理器冲突时采用同一“保留系统图标可用”的处理原则。

日期需求仍保留，但系统时钟／通知中心并非普通可移动状态项。隐藏日期文字不等于折叠整个时钟，首轮不修改时钟设置。
